# 蜡笔隐私投屏浏览器 PRD

> 版本：v0.2
> 日期：2026-08-09
> 状态：产品评审稿
> 产品名称：蜡笔隐私投屏浏览器（Crayon Private Cast Browser）
> 产品平台：Windows、macOS、Linux；未来适配 HarmonyOS

## 1. 产品摘要

蜡笔隐私投屏浏览器是一款跨平台、开源、隐私优先的投屏浏览器。桌面端统一采用 Chromium/CEF，未来 HarmonyOS 采用 ArkUI/ArkWeb，并通过同一产品协议、共享核心与一致的隐私语义提供统一体验。用户在浏览器中正常访问网站、登录并主动播放内容后，可以将当前标签页或符合安全策略的当前视频投到自己配对的蜡笔投屏接收端。

产品不定位为视频解析器、内容聚合器或多账号反检测工具。核心价值是：

1. **浏览即投屏**：不复制网址到其他工具，不离开当前页面。
2. **隐私优先**：默认临时会话，本机数据最小化，遥测默认关闭。
3. **自有接收端闭环**：自动发现或投屏码配对，只投蜡笔接收端。
4. **双投屏模式**：未知站点优先投完整标签页；安全、兼容的内容可高清直投。
5. **公开可审计**：核心客户端、协议和隐私行为开源，提供可复现构建。

## 2. 背景与机会

当前 `get-video` 已具备网页视频提取、动态嗅探、本地 relay、HLS/DASH/MP4 支持、DRM/失效流识别和局域网播放地址生成能力，但现有 UI 更接近“输入网址后解析”，投屏动作实际是复制局域网播放地址，未形成设备发现、配对和播放控制闭环。

产品形态升级为可见浏览器后，用户行为从“后台解析内容”变为“正常浏览、主动播放、投到自己的设备”，同时可以复用现有 Rust 媒体能力并降低登录态割裂、反爬页面无法加载和隐藏 WebView 无用户手势等问题。

## 3. 产品定位

### 3.1 一句话定位

> 一个默认无痕、减少追踪，并能把当前网页安全投到蜡笔接收端的开源 Chromium 浏览器。

### 3.2 核心品类

- 主品类：隐私浏览器。
- 差异化能力：网页投屏。
- 配套生态：蜡笔投屏接收端。
- 非目标品类：视频解析工具、影视聚合平台、下载器、反检测指纹浏览器、批量多账号工具。

### 3.3 品牌表达

推荐表达：

- 无痕浏览。
- 防追踪与站点数据隔离。
- 当前页一键投屏。
- 浏览数据留在本机。
- 只连接自己的蜡笔接收端。

禁止表达：

- 全网解析、VIP 解析、破解。
- 免广告、跳广告、无广告线路。
- 防封号、防关联、账号矩阵、养号。
- 完全匿名、无法追踪。

## 4. 产品原则

1. **用户主动触发**：只有用户已在当前页主动开始播放，投屏入口才进入可用状态。
2. **页面体验优先**：不得主动屏蔽、快进或跳过站点广告，不改变网站商业流程。
3. **连续观看优先**：默认从当前进度继续播放；“从头播放”由用户二次选择。
4. **不确定即降级**：无法确认广告连续性、媒体授权状态或协议兼容性时，使用标签页投屏，不进行高清直投。
5. **DRM 不碰**：不解密、不注入 CDM 绕过、不逆向许可证、不规避设备或账号限制。
6. **媒体不上云**：云端只允许承担短期配对和控制信令，不代理、缓存或分发媒体。
7. **本机最小化**：默认不保留历史、Cookie、缓存、表单、搜索词和媒体 URL。
8. **防追踪而非伪装身份**：降低指纹熵、隔离存储，不批量制造虚假设备指纹。
9. **同一产品、多个平台后端**：产品能力、协议、策略和隐私承诺统一；浏览器内核、采集、编码、安全存储和安装更新按平台适配。
10. **能力可降级、语义不降级**：平台缺少某项技术能力时，可以降级到标签页投屏或暂不支持，但不得放松 DRM、配对、隐私和数据生命周期规则。

## 5. 目标用户与核心任务

### 5.1 目标用户

| 用户类型 | 主要需求 | 当前痛点 |
|---|---|---|
| 家庭影音用户 | 把电脑网页视频投到电视 | 复制 URL 麻烦，接收端兼容性不确定 |
| 重视隐私的普通用户 | 浏览后不留下本机记录 | 主流浏览器隐私设置复杂、遥测不透明 |
| 经常使用网页播放器的用户 | 登录后直接投屏 | 独立投屏工具与浏览器登录态割裂 |
| 开源用户与开发者 | 审计隐私与投屏行为 | 闭源工具无法确认是否上传浏览数据 |

### 5.2 Jobs to Be Done

- 当我在网页中开始播放内容时，我希望一键投到电视，并保持当前播放体验。
- 当我使用共享电脑浏览和登录时，我希望关闭窗口后清除本机痕迹。
- 当网站不能高清直投时，我希望产品自动选择兼容模式，而不是给出不可播放的地址。
- 当我选择接收设备时，我希望确认它是自己的蜡笔设备，而不是局域网中的未知设备。

## 6. 范围定义

### 6.1 P0 范围

- 桌面端 CEF 浏览器壳：地址栏、标签页、前进、后退、刷新、停止、页面缩放。
- 默认隐私会话。
- 用户播放状态识别。
- 当前标签页投屏。
- MP4/HLS 基础高清直投及自动降级。
- 蜡笔设备自动发现。
- 六位投屏码配对。
- 播放、暂停、继续、停止、进度同步、音量控制。
- DRM、流失效、设备不兼容提示。
- 本机 relay 会话化和访问控制。
- Windows、macOS、Linux 的安装包、签名/校验和更新能力。
- 三个平台共享同一功能契约和自动化一致性测试；具体发布日期由各自发布门禁决定。

### 6.2 P1 范围

- DASH 音画双轨直投。
- 命名隐私空间/常用空间。
- 基础防追踪、第三方 Cookie 策略、HTTPS 优先。
- 标准/严格两档指纹保护。
- 字幕轨、音轨选择。
- 多设备收藏与设备能力缓存。
- 可复现构建和 SBOM 发布。
- HarmonyOS ArkWeb 技术预览：基础浏览、用户播放识别、配对和投屏控制闭环。

### 6.3 P2 范围

- HarmonyOS 正式版（以前置技术验证和平台审核通过为条件）。
- 移动端遥控器。
- 多房间设备组，但不做向公众分享。
- 与内容方或平台官方投屏接口合作。
- 在明确授权场景下扩展高质量直投站点。

### 6.4 明确不做

- 视频下载、录制、离线缓存。
- 内容搜索、片库、榜单、推荐、线路聚合。
- 云端媒体代理、分享链接、跨用户转发。
- DRM 解密或许可证绕过。
- 广告屏蔽、快进、跳过。
- 批量账号、Cookie 导入导出、代理池、自动化养号。
- 任意可编程浏览器指纹模板。
- 无用户播放行为的后台全网嗅探。

### 6.5 平台支持策略

| 平台 | 浏览器后端 | 产品定位 | 发布要求 |
|---|---|---|---|
| Windows 10/11 | CEF | 桌面正式版 | 通过完整功能、隐私、安全、签名和更新门禁 |
| macOS 12+ | CEF | 桌面正式版 | 通过完整功能、隐私、安全、公证和更新门禁 |
| 主流 Linux 发行版 | CEF | 桌面正式版；必要时先 Beta | 通过 Wayland/X11、PipeWire、打包和更新门禁 |
| HarmonyOS | ArkUI/ArkWeb | 未来版本/技术预览 | ArkWeb 能力、NDK 共享核心、录屏/音频和应用市场审核均验证通过 |

“跨平台”不等于一份二进制包。产品需求、交互、协议和共享核心不按 Windows/macOS 拆分，但每个平台必须有独立的采集、编码、安全存储、权限、安装包和质量门禁。平台尚未通过门禁时，不得仅因其他平台已发布而宣称支持。

## 7. 核心体验

### 7.1 首次启动

1. 展示三个核心承诺：默认无痕、数据留在本机、只投自己的接收端。
2. 简明说明无痕边界：不保留本机记录，但网站、网络提供者仍可能看到访问行为。
3. 遥测默认关闭；用户可自愿开启匿名崩溃报告。
4. 提供“开始隐私浏览”和“创建常用空间”两个入口，默认突出隐私浏览。

### 7.2 浏览与播放

1. 用户在地址栏输入网址并访问。
2. 页面完整呈现，网站广告和交互不被修改。
3. 浏览器识别到媒体元素和网络候选，但不自动启动投屏。
4. 只有发生可信用户交互且媒体进入播放状态后，工具栏投屏按钮才高亮。
5. 多视频页面默认选择最近被用户操作、正在播放且可见面积最大的媒体。

### 7.3 投屏主流程

1. 用户点击工具栏“投屏”。
2. 浏览器展示当前媒体标题、当前进度和推荐投屏方式。
3. 用户选择已配对设备，或使用自动发现/投屏码添加设备。
4. 策略引擎选择模式：
   - 满足高清直投门禁：推荐“高清直投”。
   - 不满足或无法确认：推荐“投当前标签页”。
5. 默认选择“从当前位置继续”。
6. 用户可展开选择“从头播放”；如果直投不能保证页面编排和广告连续性，则自动切换为标签页投屏或提示限制。
7. 接收端首帧出现后，浏览器显示遥控面板。
8. 用户停止、关闭标签页或会话超时后，媒体 relay token 立即失效。

### 7.4 投屏方式

| 模式 | 传输内容 | 优点 | 使用条件 |
|---|---|---|---|
| 标签页投屏 | 当前标签页画面与声音 | 保留页面、广告、字幕、弹幕和交互 | 默认兜底，未知站点优先 |
| 高清直投 | 接收端直接拉取 MP4/HLS/DASH | 清晰度高、低延迟、电脑负载低 | 通过 DRM、广告连续性、请求头、设备能力和协议门禁 |

### 7.5 广告连续性规则

- 不检测或操作“跳过广告”按钮。
- 不对广告视频修改 `currentTime`、播放速率或可见性。
- 不按广告域名过滤媒体候选。
- 服务端拼接广告随媒体流正常投送。
- 客户端广告与正片分离、无法在接收端复现播放器编排时，不允许以“从头高清直投”作为默认行为。
- 用户已经在电脑端看过广告，只能作为风险判断背景，不能作为“接收端必然保留广告”的技术结论。

## 8. 隐私产品设计

### 8.1 隐私会话

- 默认开启。
- 会话内 Cookie、缓存和站点存储可以正常工作。
- 关闭全部隐私窗口后清理历史、Cookie、缓存、LocalStorage、IndexedDB、Service Worker 数据和权限临时授权。
- 下载文件和用户主动保存的书签不会自动删除，操作前明确提示。
- 不参与浏览器账号同步。

### 8.2 常用空间

- 用户主动创建并命名，例如“家庭影音”。
- 每个空间具有独立 Cookie、缓存、权限和本地存储。
- 空间之间不得共享登录态。
- 敏感配置使用操作系统安全存储保护。
- 支持“一键销毁空间”。
- 不提供批量复制空间、批量导入 Cookie、批量代理或自动化控制。

### 8.3 防追踪与防指纹

标准模式：

- 常见跟踪器拦截。
- 第三方 Cookie 限制。
- 跨站存储隔离。
- 引用来源最小化。
- HTTPS 优先。
- 权限按站点管理。

严格模式：

- 在兼容性允许范围内限制 Canvas、WebGL、Audio、字体和硬件信息暴露。
- 统一而非为每个空间随机生成身份。
- 明确提示严格模式可能导致验证码、登录、播放器或支付异常。

禁止能力：

- 自定义任意 UA/显卡/时区/Canvas 指纹组合。
- 按账号制造稳定且不同的伪装身份。
- 网站风控绕过承诺。

### 8.4 数据处理矩阵

| 数据 | 默认存储 | 默认上传 | 生命周期 |
|---|---|---|---|
| 隐私会话历史 | 否 | 否 | 仅内存 |
| 隐私会话 Cookie/缓存 | 临时 | 否 | 关闭全部隐私窗口后删除 |
| 常用空间 Cookie | 本机 | 否 | 用户删除空间或过期 |
| 媒体候选 URL | 临时 | 否 | 投屏会话结束即删除 |
| 完整 Cookie/Authorization | 不进入投屏协议 | 否 | 浏览器内部按站点使用 |
| 已配对设备公钥 | 本机安全存储 | 否 | 用户解除配对 |
| 六位投屏码 | 临时 | 信令服务器可见 | 60～120 秒 |
| 崩溃报告 | 否，需用户开启 | 用户开启后上传 | 按隐私政策 |
| 媒体内容 | 不缓存 | 否 | 仅局域网流式传输 |

## 9. 设备与配对

### 9.1 自动发现

- 同一局域网通过 mDNS 和蜡笔自定义 UDP 广播发现。
- 列表展示设备名称、房间、在线状态、支持协议和编码。
- 未配对设备不能直接接收播放命令。

### 9.2 投屏码

- 接收端显示六位短期码。
- 浏览器输入后完成设备身份校验和密钥交换。
- 云端只做 rendezvous，不接触媒体 URL、Cookie 或媒体内容。
- 码超时、输错多次或设备确认取消后立即失效。

### 9.3 设备管理

- 重命名设备。
- 查看能力：H.264/HEVC/AV1、AAC/EAC3、MP4/HLS/DASH、最高分辨率和 HDR。
- 解除配对。
- 查看最近一次连接时间，但默认不保存播放历史。

## 10. 状态与错误设计

| 场景 | 用户提示 | 产品行为 |
|---|---|---|
| 尚未主动播放 | “请先在本页开始播放” | 禁用投屏 |
| 未发现设备 | “未找到蜡笔接收端，可输入投屏码” | 提供刷新和输入码 |
| DRM | “该内容受版权保护，暂不支持投屏” | 禁止直投和任何绕过 |
| 高清直投不安全 | “为保留完整页面体验，将投当前标签页” | 自动降级 |
| 编码不兼容 | “接收端不支持当前编码” | 尝试标签页投屏；不默认转码 |
| 流地址失效 | “媒体会话已失效，请在页面重新播放” | 清理 session |
| 网络中断 | “接收端连接中断，正在重连” | 有界重试，超时停止 |
| 隐私数据清理失败 | 明确告警并提供重试 | 不静默宣称已清理 |
| 平台缺少能力 | “当前系统暂不支持该模式，将使用兼容模式” | 按能力清单降级，不改变安全策略 |
| 本地网络权限未开启 | “请允许访问本地网络以发现接收端” | 提供系统设置指引和投屏码备选入口 |
| 网页可播放但受 DRM 保护 | “可在本机观看，该内容暂不支持投屏” | 浏览与投屏能力分离，不把网页播放失败误报为投屏限制 |

## 11. 功能验收标准

### 11.1 浏览器

- Windows、macOS、Linux 分别通过主流站点登录、跳转、输入法、字体、无障碍、iframe、音视频和下载基础兼容测试。
- 隐私窗口关闭后，自动化测试无法从新会话读取前一会话的历史、Cookie 和站点存储。
- 常用空间之间无法互读 Cookie 和站点存储。
- 同一站点在各支持平台上的隐私策略、权限默认值、媒体判断结果和用户提示保持一致。
- HarmonyOS 技术预览必须通过同一协议与隐私一致性测试；ArkWeb 缺失能力必须在产品能力清单中显式降级。

### 11.2 投屏

- 未发生用户主动播放时不得开始投屏。
- 设备首次配对必须经过接收端可见确认或短期码。
- 标签页投屏 P95 首帧时间不超过 5 秒，局域网 P95 端到端延迟目标不超过 1.5 秒。
- 高清直投 P95 首帧时间不超过 4 秒。
- 连续播放 30 分钟无崩溃、无 session 泄露、无开放代理行为。
- 停止后 10 秒内，旧媒体 token 必须不可访问。
- DRM 内容不得产生可用直投 URL。
- 多网卡、IPv4/IPv6、VPN 开关、睡眠唤醒和网络切换后不得误连未知设备或继续使用过期会话。

### 11.3 隐私

- 默认遥测关闭。
- 投屏信令不得包含 Cookie、Authorization、浏览历史或完整页面正文。
- relay 不向局域网暴露通用提取 API 和任意 URL 代理。
- 所有隐私承诺具备自动化测试或可审计实现，不使用无法验证的营销描述。

### 11.4 跨平台发布门禁

- 每个平台具备独立 CI 构建、签名/公证、SBOM、依赖漏洞扫描、升级与回滚测试。
- 浏览器内核安全更新进入稳定版后，目标 14 天内完成三桌面平台评估和发布；高危漏洞按应急流程加速。
- `CastPolicyEngine`、配对协议、relay token、隐私清理和错误语义通过共享契约测试，平台实现不得自行改写。
- 标签页采集、系统音频、硬件编码、安全存储、休眠恢复和权限撤销分别通过平台原生测试。
- 若 H.264/AAC、Widevine/CDM 或其他专有组件的许可和分发条件未确认，对应能力不得进入发布包或营销承诺。

## 12. 成功指标

### 12.1 北极星指标

> 用户主动发起的投屏会话中，接收端在 10 秒内成功出首帧并稳定播放 10 分钟的比例。

### 12.2 核心指标

- 投屏发起成功率。
- 首帧成功率与 P50/P95 时间。
- 10 分钟、30 分钟稳定播放率。
- 自动发现成功率、投屏码配对成功率。
- 高清直投命中率与降级率。
- DRM/失效/不兼容误判率。
- 崩溃率和隐私数据清理失败率。
- 用户主动开启匿名遥测的比例。

统计原则：指标默认在本机计算；只有用户明确开启匿名遥测后上传聚合值，禁止上传完整 URL、页面标题和媒体地址。

## 13. 合规门禁

- 产品化代码移除全部广告过滤、快进和跳过行为。
- 不为 VIP、DRM、签名算法或反爬措施提供绕过实现。
- 不在产品中展示提取到的原始媒体 URL。
- relay 仅服务当前用户、当前会话、已配对设备。
- 不把媒体送入云端。
- 不做内容聚合或公开分享。
- 商业发布前由知识产权和隐私律师按最终代码、文案、站点策略和接收端协议复审。
- 法务复审未通过的站点不得进入高清直投允许列表。
- 建立编解码器与 CDM 许可清单；CEF/Chromium 开源许可不自动覆盖 H.264、AAC、Widevine 等专有组件的专利、授权和分发义务。
- 分别完成 Windows、macOS、Linux 与 HarmonyOS 的应用签名、自动更新、系统权限和应用市场规则审查。

## 14. 待决策问题

1. 桌面正式版是否要求 Windows、macOS、Linux 同日 GA，还是统一版本线下按门禁分批发布；建议架构与开发并行，发布日期允许分波次。
2. Linux 首个正式支持范围是 Wayland + PipeWire，还是同时承诺 X11 与多个发行版打包格式。
3. 接收端现有播放器是否支持 WebRTC、HLS、DASH 和双轨同步。
4. 标签页投屏各平台优先采用浏览器采集还是原生窗口/标签页采集 + 硬件编码。
5. 投屏码是否依赖蜡笔云信令，是否需要支持完全离线配对。
6. P0 是否提供常用空间，还是只提供默认隐私会话。
7. 高清直投允许列表由谁审批、如何版本化、如何紧急下线。
8. 开源范围：浏览器壳、Rust Core、接收端协议、信令服务分别采用何种许可证。
9. 是否商业分发 H.264/AAC 和 Widevine/CDM；由谁承担专利、授权、签名和地区分发评估。
10. HarmonyOS 第一阶段定位为手机/平板浏览投屏，还是面向 PC 形态；两者的 ArkWeb、采集和应用审核范围不同。
